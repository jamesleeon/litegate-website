客户案例 · Lite 生态

一个电商 ISV 小团队，如何用几个单文件程序跑生产

这个团队为大量电商商家提供 SaaS 服务，同时给大客户做私有化部署。人手不多，不想为了部署和服务治理再养一套 Kubernetes。他们把入口交给 LiteGate，用 litedeploy 发布服务；服务之间需要加密时加上 litemesh，存量的 Consul 老服务原样保留；办公室和门店的内网用户通过 LiteDNS 直连网关。几个单文件程序覆盖了入口、部署、服务发现和内网解析，机器和运维成本都明显降了下来。

行业
电商 ISV（SaaS + 私有化交付）
团队
小团队，开发兼运维
起点
一批跑在 Consul 上的老服务
用到的组件
LiteGate · litedeploy · litemesh · LiteDNS

四个组件

他们用到的四个组件：各管一件事，用到才加

每个组件都是一个 Go 二进制，没有外部依赖；LiteGate、litedeploy、litemesh 自带 Web 控制台和 MCP，LiteDNS 刻意保持为一个只做解析的小程序。只有 LiteGate 是必需的；大多数小团队加上 litedeploy 就够用了。

必选

LiteGate

入口网关 · 类似 Nginx / Traefik / Caddy

所有外部流量的唯一入口：路由、自动证书、负载均衡、认证、内网发布（Connect）、实时推送；可同时接多个服务发现源，日志和链路接入现有监控。

了解 LiteGate
推荐

litedeploy

部署与调度 · 类似 Nomad

把二进制包或 Docker 镜像发布到各台机器，支持批次发布、健康检查和失败恢复。服务实例注册到 litedeploy，LiteGate 直接订阅，不需要再部署注册中心。

  • Raft 强一致，多 Server 自动选主
  • Agent 通过 gRPC 长连接接收指令
按需

litemesh

服务网格控制面 · 类似 Consul

服务之间也要 mTLS 加密认证，或者需要配置中心、分布式锁、跨机房服务发现时再加。就像 Nomad 自己能做服务发现，需要更多时才配 Consul。

  • 内置 CA，无 Sidecar 的服务间 mTLS
  • KV、Session、锁；Gossip 组网，无主节点
按需

LiteDNS

内网解析 · 轻量本地 DNS

办公室、门店、机房里的用户访问同一个域名时，直连网关的内网地址，同一张证书内外通用。内网有多台网关时，每次只返回一个节点 IP 并轮询，宕机节点自动摘除。

  • 只拦截网关和服务域名，其余交给 CamoDNS 或企业现有 DNS
  • 也能把已有的 Nacos 等注册中心接给 LiteGate

放在一起

它们之间怎么配合

虚线框是按需加入的组件。LiteGate 可以同时从 litedeploy、litemesh 和存量的 Consul 发现服务，访问日志和链路送到你已有的监控平台。

多源发现

新老服务并存，不用一次迁完

这个团队就是这样做的：新服务注册到 litemesh，一批老服务继续留在 Consul 里，不再改动。LiteGate 同时订阅多个发现源，所有实例都变成同一种服务端点，用同一套 litegate.* 标签生成路由。迁移可以按服务一个个来，网关配置不用跟着改。

litedeploy、Docker、Kubernetes、Nomad 也都可以作为发现源同时接入。

服务发现源总览
config.yaml
service_discovery:
  catalogs:
    - enabled: true
      provider: litemesh     # 新服务
      url: http://10.0.0.6:8080
    - enabled: true
      provider: consul       # 存量老服务
      url: http://10.0.0.7:8500

接入监控体系

日志和链路，直接进你现有的平台

  • 访问日志：JSON 输出到控制台或文件（自带轮转），由 Filebeat、Vector、Promtail 采集进 ELK 或 Loki；流量大时用 Webhook 批量投递到消息队列。也可以用模板输出类 Nginx 格式。
  • 分布式追踪：按 OTLP/HTTP 把链路发到 OpenTelemetry Collector，再进 Jaeger、Tempo 等；支持采样率，访问日志里带 trace_id，日志和链路能对上。
  • 指标：Prometheus 格式，配合官方 Grafana 面板。
访问日志 Trace ID 与链路
config.yaml
log:
  format: json
  access_log:
    enabled: true
    file_enabled: true
    file: ./logs/access.log   # 交给采集器
tracing:
  enabled: true
  endpoint: http://otel-collector:4318
  sample_ratio: 0.1

内网多节点

内网 5 台网关，流量也要均匀

这个团队在内网部署了 5 个 LiteGate 节点。如果让普通 DNS 一次返回 5 个 IP，大多数客户端只连第一个，代码不改的话流量会全部压到一台上。LiteDNS 在 DNS 这一层就把负载分开：

  • 每次只返回一个节点 IP，按域名轮询，不同的请求方拿到不同的节点，业务代码不用改。
  • 每个 LiteGate 节点把自己的内网 IP 发布到 litemesh，并定时心跳续约；LiteDNS 实时监听这些记录。
  • 节点正常停机会立即撤下自己的记录；宕机时租约到期自动摘除，LiteDNS 还会定期全量重扫兜底，坏节点不会一直被分配出去。
LiteDNS · rules.yaml
upstreams:
  gateway_kv: {type: litemesh,
               servers: ["http://10.0.0.6:8080"],
               token: "env://LITEMESH_TOKEN"}
  corp_dns:   {servers: ["udp://10.0.0.53:53"]}
rules:
  # 每次 1 个 IP，轮询
  - {name: gateway-sites, suffixes: [example.com],
     upstream: gateway_kv, fallback: corp_dns,
     answer: {order: round_robin, limit: 1, ttl: 10}}
  - {name: default, upstream: corp_dns}

怎么组合

跟着业务长大，一次只加一个

一台服务器

只用 LiteGate

官网、后台、几个 API，一台云主机就够。网站、反向代理、证书、状态页都在网关上。

服务多起来

+ litedeploy

需要在多台机器上发布、扩容和回滚。服务一上线，LiteGate 自动加上路由。大多数小团队到这一步就够了。

服务间要加密

+ litemesh

服务之间的调用也要 mTLS，或者需要配置中心、分布式锁、多机房。

内网也走网关

+ LiteDNS

办公室、门店和客户机房里的用户也要直连网关，内网多台网关需要均匀分流；或者已经有 Nacos，想接给 LiteGate。

最常用的组合只要一段配置

LiteGate 订阅 litedeploy 的服务注册。业务服务注册时带上 litegate.http.path 之类的标签，就会自动出现在网关上；实例下线自动摘除。

服务发现源总览
LiteGate · config.yaml
service_discovery:
  catalogs:
    - enabled: true
      provider: litedeploy
      url: http://10.0.0.5:8080  # litedeploy Server
      token: "replace-with-token"
      default_domain: example.com

成本

钱省在哪里

同样的需求，常见做法要拼好几套系统，每套都要机器、要升级、要有人懂。这个团队用四个单文件程序覆盖了这些需求。

需求常见做法Lite 生态
入口与证书Nginx + Certbot，或 Ingress + cert-managerLiteGate，证书自动申请续期
部署与调度Kubernetes 集群，或 Jenkins + 脚本litedeploy
服务发现Nacos / Consul / etcd 集群litedeploy 自带；要 mTLS 时加 litemesh
配置中心与锁Nacos / Apollo、Redis 锁litemesh KV 与锁（按需）
内网穿透与私有化frp、VPN、给客户开放端口LiteGate Connect，客户机房不开入站端口
内网解析与分流手工维护 hosts；内网 DNS 返回多个 IP，客户端只连第一个LiteDNS：每次一个节点 IP 轮询，宕机自动摘除
实时推送MQTT、自建 WebSocket 服务LiteGate 事件通知
日志与链路解析 Nginx 日志、各服务自己埋点LiteGate JSON 访问日志 + OTLP 链路，直接进现有平台
监控大屏Prometheus + Grafana 全套内置控制台和状态页，也能接 Grafana

机器少

不需要 Kubernetes 控制面节点和托管集群费用，也不用为注册中心、配置中心单独准备机器。几台普通云主机就能跑起整套业务。

私有化交付轻

给客户部署时只带几个二进制。客户机房通过 Connect 主动连出来，不用开放入站端口，远程运维也走同一条加密隧道。

运维人手少

单文件、YAML、热加载，排错有控制台和状态页；LiteGate、litedeploy、litemesh 都内置 MCP，日常的发布、配置和排障可以交给 AI 助手。
