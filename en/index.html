Architecture

One entry point between the internet and all of your services

On the left, HTTP, TCP, and UDP traffic from the internet. On the right, your backends: services discovered through tags, servers declared in site files, and private services reached through the Connect reverse tunnel. The routing engine in the middle forwards traffic, with security, traffic management, certificates, and observability in one place.

Service discovery · Magic Ingress

Backends go live when they register. No gateway config.

As an API gateway, LiteGate needs one site file for the frontend. After that, each backend service adds two tags when it registers and is mounted under the same domain. Releasing, scaling, or retiring a service needs no gateway changes and no restart.

  1. The service registersBackends register in Litemesh, Consul, Docker, or Kubernetes, with tags in their service metadata or Docker labels.
  2. The gateway follows in real timeLiteGate watches for changes, builds routes in memory, and merges them with the frontend from the site file onto one domain: same origin, no CORS to configure.
  3. Traffic tracks the instancesNew instances join load balancing automatically; instances that fail health checks or deregister are removed. New domains get certificates as usual.

Site YAML v2

One config language, from three lines to a full gateway

Paths are keys, actions are values. Simple sites take a few lines; load balancing, CORS, and rate limits go right under the route they apply to, with no format switch and no extra plugins.

Frontend and API

/api goes to the backend; everything else is the SPA, with unknown routes falling back to index.html.

site: app.example.com
/api: 127.0.0.1:8080
spa: ./dist

Several backends, prefix stripped

Comma-separate addresses for round-robin by default; strip_prefix removes /v1 before forwarding.

site: api.example.com
/v1:
  proxy: 10.0.0.5:8080, 10.0.0.6:8080
  strip_prefix: true

CORS and rate limiting

Policy sits on the same route as the forwarding; the gateway answers preflight requests itself.

site: api.example.com
/api:
  proxy: localhost:8080
  cors:
    allowed_origins: [https://web.example.com]
  rate_limit: {rate: 10, key: ip}

Order doesn't matter

Routes are ordered by priority and match specificity, not by where they appear in the file. Two routes with identical match conditions are an error rather than a silent override.

Shorthand to full form, same format

When you need exact paths, method or header matching, or reusable named services, add routes and services to the same file. Shorthand and full forms mix freely.

Tool friendly

It's just YAML: editor highlighting, litegate -t validation, versioning in Git, and AI assistants can create and edit sites through the built-in MCP server.

Connectivity

Publish private services, reach cloud resources, centralize egress

Three directions, three features, all on the same port 443. No frp, bastion host, or separate proxy service to deploy.

CONNECT

Publish private services to the internet

The internal node dials out to the cloud, so homes and data centers open no inbound ports. One Cloud serves many Homes, and each Home can only publish the domains it is authorized for. TLS terminates on the internal node: private keys never leave it and the cloud never sees plaintext.

Connect guide
Home · config.yaml
connect:
  client:
    enabled: true
    name: home
    remote: https://connect.example.com
    token_file: /etc/litegate/secrets/home.token
    publish_sites: true
FORWARD

Reach cloud databases from your laptop, safely

Map MySQL, Redis, or SSH inside a VPC to a port on a developer's machine. The server locks the domain to one Stream, so clients cannot choose another target, and the Stream's IP rules, session limits, and timeouts still apply.

Database access guide (Chinese)
laptop
$ litegate forward \
    --remote https://db-tunnel.example.com \
    --local 127.0.0.1:3306 \
    --token-file ./rds.token
FORWARD PROXY

Egress for machines without a public IP

A standard HTTP CONNECT forward proxy, mounted on 443 and triggered by hostname. It supports account authentication and destination ACLs; with probe resistance on, unauthenticated requests just see an ordinary website.

Forward vs Forward Proxy (Chinese)
config.yaml
ingress_plugins:

    type: forward_proxy
    entrypoints: [websecure]
    config:
      hosts: [proxy.example.com]
      username: ops
      password_env: LITEGATE_PROXY_PASSWORD
      probe_resistance: true

Notify Hub

POST one message, every subscriber gets it

Config changes, finished jobs, ticket alerts: these used to need an MQTT broker, or a home-grown WebSocket service with its own connection table. Now the gateway is the notification hub. Publishers send a single HTTP POST; browsers, Go services and gateway plugins subscribe, with offline delivery when you need it.

Before
  • Run and operate an MQTT broker or a custom WebSocket service
  • Integrate an MQTT / WebSocket SDK into every client
  • Backends track connections, heartbeats and cross-instance broadcast
Now
  • Two more routes on the gateway, no extra service
  • Publishers POST over HTTP; subscribers hold one HTTP stream
  • Authentication, quotas and monitoring come from the gateway
  1. PublishAnything that speaks HTTP POSTs a message to the gateway. No MQTT client, no broker connection.
  2. BroadcastThe gateway hands the message to NATS, which reaches every gateway node across instances and sites.
  3. SubscribeBrowsers and Go services subscribe over SSE; gateway plugins declare a subject and receive it directly. Clients reconnect automatically and reload state on connect, so anything missed while offline is caught up.
Event notification guide (Chinese)
sites/app.yaml
site: app.example.com
/notify/:                    # publish: POST /notify/<topic>
  ip_restriction: { allow_ips: [10.0.0.0/8] }
  action:
    type: nats
    mode: publish
    subject_from: path.1       # /notify/config → notify.config
    subject_prefix: notify
    subject_allowlist: [config, order]
/events/config:              # subscribe
  use: login                  # login check
  action:
    type: nats
    mode: subscribe
    subject: notify.config
    sse: { tenant: app }

provider.gothe plugin owns its subject
func (p *Provider) NotifySubjects() []string {
    return []string{"notify.tenant"}
}
func (p *Provider) HandleNotify(
    ctx context.Context, n plugin.Notification) error {
    if n.Resync { p.cache.InvalidateAll(); return nil }
    // tenant disabled: drop just that tenant
    p.cache.Invalidate(tenantOf(n.Data))
    return nil
}

Offline delivery

When every message must arrive, turn on JetStream persistence: offline subscribers resume where they left off and acknowledge after processing. One subscriber's ACK never affects the others.

Durable events

No long-lived connections in your backend

Push, heartbeats, reconnects and slow clients are handled by the gateway. Backends stay stateless HTTP services and scale out without thinking about broadcast.

Plugins subscribe too

An IDS plugin can cache tenants safely: declare notify.tenant and a tenant disabled in your tenant system is dropped from every gateway's cache within seconds.

Encrypted ClientHello

Encrypt even which site is visited

Plain HTTPS exposes the domain name (SNI) in the clear during the handshake. With ECH, the network sees only a public name; the real domain is encrypted inside the ClientHello, and LiteGate decrypts it to pick the certificate and route as usual.

  • Generates ECH keys and publishes HTTPS (type 65) records through your DNS provider
  • Sites keep using ordinary ACME certificates
  • Multiple public-name groups; keys stored in files or cluster KV
  • Clients without ECH keep working unchanged
ECH guide
config.yaml
ech:
  enabled: true
  public_name: ech.example.com   # the only name on the wire
  dns_provider: cloudflare
  domains:                       # real sites to hide
    - app.example.com
    - admin.example.com

Automatic certificates

Automatic certificates, even at home

Give a site a domain and its certificate is obtained and renewed automatically. On home networks where port 80 is unreachable, configure a DNS provider and the whole zone switches to DNS-01. Failures back off instead of exhausting the CA's rate limits.

  • HTTP-01, TLS-ALPN-01, DNS-01 (wildcards)
  • Aliyun, Cloudflare, Huawei Cloud, and Tencent Cloud built in; more via plugins
  • On-Demand TLS for SaaS customers bringing their own domains
  • Local CA: trusted HTTPS for *.localhost development
config.yaml · home network
auto_cert:
  dns_providers:
    - name: cloudflare
      type: cloudflare
      enabled: true
      domains: ["*.home.example.com"]
      config:
        api_token: env://CF_API_TOKEN
# The wildcard is issued first and reused by new sites;
# other names in the same zone also use DNS-01

L4 + L7

Websites and TLS services share 443

LiteGate reads the SNI before the TLS handshake and hands matching connections to a TCP upstream; everything else continues to HTTPS. Protocols that start with TLS, such as Redis TLS and gRPC, can share 443 directly. For MySQL and PostgreSQL, which begin with a plaintext handshake, use Forward above.

streams/redis.yaml
site: tcp://redis.example.com   # matched by SNI on 443
proxy: 10.0.0.30:6380

Platform

From a single VPS to multi-tenant SaaS

Small projects only need the few lines above. As things grow, turn these on when you need them, without switching gateways.

Config release and rollback

With Release Control on, edits go to a draft first and are published only after validation and a diff review. Every release is kept, so rolling back is one step.

Multi-tenant routing (IDS)

After a route matches and before forwarding, your Go plugin identifies the tenant, allows or rejects the request, picks tenant-specific instances, and applies per-tenant rate limits.

Cluster config and shared certificates

Sites, certificates, and ECH keys can live in Litemesh or Consul KV. Write once and every node hot-reloads; one node issues a certificate and all of them use it.

Compile-time plugins

litegate build --with builds third-party plugins into the binary: Streams, Actions, middleware, load balancers, DNS providers, and more.

Built-in MCP

AI assistants such as Claude Code and Cursor can inspect sites, create configuration, hot-reload, and diagnose errors over MCP.

Security and observability

OIDC, JWT, and API key auth, IP rules, and scan protection, plus a built-in dashboard, access logs, Prometheus metrics, and tracing.

Quick start

Your first response in a minute

Install

Download a binary from Releases, or install with Go:

$ go install \
  github.com/jamesleeon/LiteGate/cmd/litegate@latest

Write a site

Create sites/hello.yaml in the working directory:

site: localhost
respond: "Hello, LiteGate!"

Run

No config.yaml needed to start:

$ ./litegate
$ curl http://localhost/
Hello, LiteGate!
