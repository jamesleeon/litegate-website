Customer story · Lite ecosystem

How a small e-commerce ISV team runs production on a few single binaries

This team serves a large number of e-commerce merchants as a SaaS and also delivers on-premises deployments for larger customers. With few people, they did not want to run Kubernetes just for deployment and service management. They put LiteGate at the entrypoint and ship services with litedeploy; litemesh joined when service-to-service calls needed encryption, the legacy services on Consul stayed exactly where they were, and office and store users reach the gateway directly through LiteDNS. A few single-binary programs cover the entrypoint, deployment, service discovery and internal DNS, and their machine and operations costs dropped noticeably.

Four components

The four components they use: one job each, added only when needed

Each component is a single Go binary with no external dependencies. LiteGate, litedeploy and litemesh include a web console and MCP; LiteDNS deliberately stays a small resolver. Only LiteGate is required, and most small teams need nothing beyond litedeploy.

Required

LiteGate

Entrypoint · like Nginx / Traefik / Caddy

The single entrypoint for outside traffic: routing, automatic certificates, load balancing, authentication, publishing private services (Connect) and real-time push; it reads several discovery sources at once and feeds logs and traces to your monitoring.

About LiteGate
Recommended

litedeploy

Deployment and scheduling · like Nomad

Ships binary packages or Docker images to your machines, with batched rollouts, health checks and failure recovery. Service instances register with litedeploy and LiteGate subscribes directly, so no separate registry is needed.

  • Raft consensus with automatic leader election
  • Agents receive commands over long-lived gRPC streams
As needed

litemesh

Service mesh control plane · like Consul

Add it when service-to-service calls need mTLS, or you need a configuration store, distributed locks or cross-site discovery. Just as Nomad can do service discovery on its own and Consul is added for more.

  • Built-in CA and sidecar-free service mTLS
  • KV, sessions and locks; gossip cluster with no leader
As needed

LiteDNS

Internal resolution · a small local DNS

Users in offices, stores and data centers reach the gateway's internal address for the same domain, with one certificate inside and out. It can also bring an existing registry such as Nacos to LiteGate.

  • Intercepts only gateway and service names; everything else goes to CamoDNS or your existing DNS

Together

How they fit together

Dashed boxes are added as needed. LiteGate can discover services from litedeploy, litemesh and an existing Consul at the same time, and send access logs and traces to the monitoring platform you already run.

Multi-source discovery

Old and new services side by side, no big-bang migration

That is exactly what this team did: new services register in litemesh, while a set of older services stays in Consul untouched. LiteGate subscribes to several discovery sources at once; every instance becomes the same kind of service endpoint and the same litegate.* tags produce its routes. Migrate one service at a time without changing gateway configuration.

litedeploy, Docker, Kubernetes and Nomad can join as sources at the same time too.

Service discovery sources
config.yaml
service_discovery:
  catalogs:
    - enabled: true
      provider: litemesh     # new services
      url: http://10.0.0.6:8080
    - enabled: true
      provider: consul       # legacy services
      url: http://10.0.0.7:8500

Your monitoring stack

Logs and traces go straight into the platform you already run

  • Access logs: JSON to stdout or a rotated file, collected by Filebeat, Vector or Promtail into ELK or Loki; at high volume, batch them to a message queue over a webhook. A template can also emit Nginx-style lines.
  • Distributed tracing: spans go over OTLP/HTTP to an OpenTelemetry Collector and on to Jaeger, Tempo and others, with a sampling ratio; access logs carry trace_id so logs and traces line up.
  • Metrics: Prometheus format, with the official Grafana dashboard.
Access log Trace ID and tracing
config.yaml
log:
  format: json
  access_log:
    enabled: true
    file_enabled: true
    file: ./logs/access.log   # for your collector
tracing:
  enabled: true
  endpoint: http://otel-collector:4318
  sample_ratio: 0.1

Adoption

Grow with the business, one component at a time

One server

LiteGate only

A website, an admin panel and a few APIs fit on one cloud server. Sites, reverse proxy, certificates and the status page all live on the gateway.

More services

+ litedeploy

You need to deploy, scale and roll back across machines. When a service comes up, LiteGate adds its route. Most small teams stop here.

Encrypt service calls

+ litemesh

Service-to-service calls need mTLS, or you need a configuration store, distributed locks or several sites.

Internal users too

+ LiteDNS

Users in offices, stores and customer data centers should reach the gateway directly; or you already run Nacos and want LiteGate to use it.

The common combination is one block of configuration

LiteGate subscribes to litedeploy's service registry. Services that register with tags such as litegate.http.path appear on the gateway automatically, and instances that go away are removed.

Service discovery sources
LiteGate · config.yaml
service_discovery:
  catalogs:
    - enabled: true
      provider: litedeploy
      url: http://10.0.0.5:8080  # litedeploy server
      token: "replace-with-token"
      default_domain: example.com

Cost

Where the savings come from

The usual way to meet the same needs stitches together several systems, each needing machines, upgrades and someone who knows it. This team covers them with four single-binary programs.

NeedUsual approachLite ecosystem
Entrypoint and certificatesNginx + Certbot, or Ingress + cert-managerLiteGate, with automatic issue and renewal
Deployment and schedulingA Kubernetes cluster, or Jenkins + scriptslitedeploy
Service discoveryA Nacos / Consul / etcd clusterBuilt into litedeploy; add litemesh for mTLS
Configuration and locksNacos / Apollo, Redis lockslitemesh KV and locks (as needed)
Private access and on-premisesfrp, VPNs, opening ports at customer sitesLiteGate Connect, with no inbound ports at the customer
Internal DNSHand-maintained hosts files, internal DNSLiteDNS (as needed)
Real-time pushMQTT, a home-grown WebSocket serviceLiteGate notifications
Logs and tracingParsing Nginx logs, instrumenting every serviceLiteGate JSON access logs + OTLP traces into your existing platform
MonitoringA full Prometheus + Grafana stackBuilt-in console and status page, with Grafana if you want it

Fewer machines

No Kubernetes control plane nodes or managed cluster fees, and no dedicated machines for a registry or configuration center. A few ordinary cloud servers run the whole business.

Lighter on-premises delivery

Customer deployments ship a few binaries. The customer site dials out through Connect, so no inbound ports are opened, and remote operations use the same encrypted tunnel.

Fewer people on operations

Single files, YAML and hot reload, with a console and status page for troubleshooting. LiteGate, litedeploy and litemesh include MCP, so routine releases, configuration and troubleshooting can go to an AI assistant.
