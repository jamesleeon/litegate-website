Use case 1

Publish a website or frontend app

  • You have a static site, a blog, or the dist directory of a Vue / React build
  • You want HTTPS without requesting and renewing certificates yourself
  • Refreshing any frontend route must work, and /api must go to the backend

Minimal configuration

sites/www.yamlstatic site
site: https://www.example.com
file_server: ./public
sites/app.yamlSPA + API
site: https://app.example.com
/api:
  proxy: localhost:8080
  strip_prefix: true   # when the backend has no /api prefix
spa: ./dist              # unknown routes fall back to index.html

The https:// prefix turns on HTTPS: HTTP requests redirect to HTTPS and the certificate is issued automatically. A bare domain stays plain HTTP by default.

Next steps

  • compress: true enables gzip / brotli / zstd (inside the / route when the site has child routes)
  • response_headers adds security headers everywhere
  • redirect moves old domains and paths while keeping the original path
  • markdown renders a docs directory as web pages; list gives a browsable download area
  • Frontend bundles in KV sync to every gateway and keep earlier versions
sites/www.yaml
site: https://www.example.com
response_headers:
  X-Frame-Options: DENY
/docs:                      # Markdown rendered as pages
  markdown: {root: ./docs}
/:                          # with child routes, root handling goes in /
  file_server: ./public
  compress: true

Use case 2

An API gateway for several backends

  • One domain serves several services that must be split by path
  • A service runs several instances and needs load balancing, health checks and retries
  • CORS, rate limits and headers should be handled once, not in every service

Minimal configuration

sites/api.yamlsplit by path
site: https://api.example.com
/users: localhost:8080
/orders: localhost:8081
/orders/export: localhost:8082  # the more specific path wins
sites/api.yamlseveral instances
site: https://api.example.com
proxy:
  to: [10.0.0.5:8080, 10.0.0.6:8080]
  lb: least_conn     # round_robin by default
  health: /health     # failing instances are removed
  retry: 2

Route order in the file does not matter: routes are ranked by path specificity and priority, and two routes with identical match conditions are an error. WebSocket and gRPC need no extra configuration.

Next steps: policies live under the route

  • cors: the gateway answers preflight requests itself
  • rate_limit: per route or per client IP
  • request_headers / response_headers: add or remove headers; a leading - removes
  • cache: reverse-proxy caching; circuit breaking, weighted routing and session affinity live in named services
  • Settings shared by several routes go into snippets and are pulled in with import
sites/api.yaml
site: https://api.example.com
/api:
  proxy: localhost:8080
  cors:
    allowed_origins: [https://web.example.com]
  rate_limit: {rate: 10, key: ip}
  request_headers:
    -X-User-Id: ""   # drop identity headers forged by clients

Use case 3 · Magic Ingress

Routes appear when services start

  • Backends run on Docker, Swarm or Kubernetes, or register in Consul / Litemesh
  • Services come and go and scale often, and you do not want to edit the gateway each time
  • The frontend and several backend services must share one domain to avoid CORS

Minimal configuration: the gateway describes the frontend, backends declare themselves

sites/app.yamlwritten once on the gateway
site: https://app.example.com
spa: ./dist

https://app.example.com/ is the frontend; /api/orders and /api/users appear as services register and disappear when instances go offline.

docker-compose.yml
services:
  orders:
    image: acme/orders
    labels:
      litegate.http.host: app.example.com
      litegate.http.path_prefix: /api/orders
  users:
    image: acme/users
    labels:
      litegate.http.host: app.example.com
      litegate.http.path_prefix: /api/users
service metadata
litegate.http.host=app.example.com
litegate.http.path_prefix=/api/orders
litegate.http.strip_path=true   # optional: strip the prefix
service metadatanamed resources
litegate.http.routers.orders.match.hosts=app.example.com
litegate.http.routers.orders.match.path_prefix=/api/orders
litegate.http.routers.orders.middlewares=orders-limit
litegate.http.middlewares.orders-limit.ratelimit.qps=100
litegate.http.services.orders.retry.attempts=2
litegate.http.services.orders.healthcheck.path=/healthz

Kubernetes users can use standard Ingress and Gateway API resources directly. LiteGate has a built-in controller, so nothing else needs to be installed.

Use case 4 · Connect

Publish private services without a public IP

  • Services run at home, in an office or in a customer's data center, without a public IP or open inbound ports
  • An on-premises system must be reachable from the cloud, which used to take frp or an open MQ port
  • TLS should terminate inside the private network so the cloud only relays ciphertext

How it works

Private nodes (Home) dial out to the cloud (Cloud). One Cloud accepts many Homes, and each Home can only publish the domains it is authorized for. Homes keep writing ordinary site files; with publish_sites on, those sites are served through the tunnel.

Home · config.yaml
connect:
  client:
    enabled: true
    name: home
    remote: https://connect.example.com
    token_file: /etc/litegate/secrets/home.token
    publish_sites: true

Use case 5 · Forward

Reach a cloud database from your laptop

  • MySQL, Redis or SSH sit in a cloud VPC and developers need to connect from their machines
  • You do not want a public database port, a jump host or a VPN
  • Private servers should reach public APIs through one controlled exit (forward proxy)

Minimal configuration

gateway · streams + sitesserver
# streams/rds.yaml: no listener of its own, used only by Forward
name: rds
protocol: tcp
listen: false
proxy: 10.0.0.20:3306
---
# sites/db-tunnel.yaml: the hostname is locked to this Stream
site: https://db-tunnel.example.com
forward:
  target: {type: stream, name: rds}
  token_file: ./secrets/forward.token
developer machineclient
$ litegate forward \
    --remote https://db-tunnel.example.com \
    --local 127.0.0.1:3306 \
    --token-file ./rds.token
$ mysql -h 127.0.0.1 -P 3306 -u app -p

Traffic is encrypted over 443 and the client cannot change the target; the Stream's IP restrictions, session limits and timeouts still apply.

Use case 6

Stop managing certificates by hand

  • You want HTTPS without running Certbot and cron jobs
  • Port 80 is blocked on your home network, or you need a *.example.com wildcard
  • You want trusted HTTPS in local development, or SaaS customers bring their own domains

Minimal configuration

Write site: https://your-domain (or https: true) and the certificate is issued automatically and renewed before it expires, over HTTP-01 by default. When port 80 is unreachable, configure a DNS provider in config.yaml; matching domains switch to DNS-01, and failures back off before retrying.

  • Alibaba Cloud, Cloudflare, Huawei Cloud and Tencent Cloud are built in; other providers come as plugins
  • If only port 80 is blocked, default_challenge: tls-alpn validates over 443
  • In cluster mode certificates live in KV: one node issues, every node shares
config.yaml · home network
auto_cert:
  enabled: true
  email: admin@example.com
  dns_providers:
    - name: cloudflare
      type: cloudflare
      enabled: true
      domains: ["*.home.example.com"]
      config:
        api_token: env://CF_API_TOKEN

Next step: encrypt even which site is visited (ECH)

Plain HTTPS exposes the domain in cleartext during the handshake. With ECH, the network only sees a public name; the real domain is encrypted inside the ClientHello. Sites keep ordinary ACME certificates, and clients without ECH connect as usual.

config.yaml
ech:
  enabled: true
  public_name: ech.home.example.com  # the only name visible
  dns_provider: cloudflare
  domains: [app.home.example.com]   # sites to hide

Use case 7

Add login and protection

  • Internal tools and admin panels must block anonymous access, or plug into your company SSO
  • APIs must validate JWTs, and backends only want verified user information
  • You need to stop scanners and abuse, or allow certain paths only from the private network

Minimal configuration

sites/app.yamlper-path protection
site: https://app.example.com
/admin:
  proxy: localhost:8081
  ip_restriction:
    allow_ips: [10.0.0.0/8, 192.168.0.0/16]
/api/login:
  proxy: localhost:8080
  rate_limit: {rate: 1, key: ip}
proxy: localhost:8080
sites/api.yamlJWT validation
site: https://api.example.com
/api:
  proxy: localhost:8080
  auth:
    type: jwt
    jwks_url: https://auth.example.com/.well-known/jwks.json
    issuer: https://auth.example.com

Next steps

  • OIDC / OAuth2 single sign-on: define auth_providers in config.yaml and reference them with remote_auth on the route; after login, claims are injected as headers for the backend (sessions are kept in Redis)
  • Already have an auth service? Delegate to it with Forward Auth
  • Rule-based WAF, scan protection and CSRF; policies shared by several routes become named middleware referenced with use

Use case 8 · Notify Hub

Push real-time messages to browsers

  • Configuration changes, finished jobs or ticket alerts must reach the frontend or other services right away
  • You do not want to run MQTT, or write a WebSocket service and maintain a connection table
  • Several gateways and backend instances all need the same message

Minimal configuration: two routes

sites/app.yaml
site: https://app.example.com
/notify:                 # publish: the key header picks the subject
  publish: notify.{header.key}
/events/config:          # subscribe to configuration notices
  subscribe: notify.config
any language
$ curl -X POST http://10.0.0.10/notify \
    -H "key: config" \
    -H "Content-Type: application/json" \
    -d '{"type":"config.changed","version":42}'
app.jsnative browser API
const events = new EventSource('/events/config')
events.onopen = () => reloadAll()        // refresh on connect
events.onmessage = e => reload(JSON.parse(e.data))
main.gostandard library only
sub := &notify.Subscriber{
    URL:     "https://app.example.com/events/config",
    OnOpen:  cache.ReloadAll,
    OnEvent: cache.Apply,
}
go sub.Run(ctx)   // reconnects with random backoff

The gateway fans messages out to every node through NATS. Push, heartbeats and reconnects are handled by the gateway, so backends stay stateless HTTP services. The example shows live notifications; protect publishing and subscribing with JWT, Forward Auth and similar. For per-message delivery, turn on JetStream offline messages.

Use case 9 · L4

TCP / UDP forwarding, with sites and TLS services sharing 443

  • You need to forward non-HTTP traffic such as databases, DNS or game servers
  • Only port 443 is open, and Redis TLS or gRPC should use it too

Minimal configuration

streams/dedicated ports
# streams/mysql.yaml
site: tcp://:3307
proxy: 192.168.1.100:3306
---
# streams/dns.yaml
site: udp://:5353
proxy: 192.168.1.100:53
streams/redis.yamlshared 443
site: tcp://redis.example.com   # matched by SNI
proxy: 10.0.0.30:6380

The gateway reads SNI before the TLS handshake and hands matching connections to the upstream whole; everything else continues into HTTPS. For protocols that start in plaintext, such as MySQL and PostgreSQL, use Forward from use case 5.

Use case 10

Status page, console and production

  • You want a public status page for users, or a live console for operators
  • LiteGate must run as a system service or container and plug into existing monitoring
  • When something fails, you want to know which route a request took and why it was rejected

One block of configuration each

sites/status.yamlpublic status page
site: https://status.example.com
status:
  title: Service status
  host: "*"              # default: only the current site
  show_instances: true   # show each backend instance

It can also hang off an existing site: /status: {status: {}}. The data comes from real gateway traffic, with no probes to install.

config.yamldashboard
dashboard:
  enabled: true
  port: 9999
  username: ops
  password: "$2a$10$..."   # from litegate -hash

Live throughput and latency, routes and service tags, access logs, certificates, Connect tunnels and compiled plugins, plus in-browser site editing. Keep this port on the private network.

Common commands

  • litegate -init creates directories and an example configuration; litegate -t validates before launch
  • litegate systemd prints a systemd unit; litegate healthcheck serves container health checks
  • Prometheus metrics, access logs and trace IDs follow each request; import the official Grafana dashboard
  • When a route does not match, ask the AI to simulate the request over MCP; see use case 12
terminal
$ litegate -init         # directories and example config
$ litegate -t            # validate configuration
$ litegate -hash 'pwd'   # bcrypt password hash
$ litegate systemd       # print a systemd unit

Use case 11

Grow from one VPS to a multi-tenant SaaS

  • Several gateways form a cluster and sites and certificates need central management
  • Requests must be identified by tenant, admitted, routed to tenant-specific instances and rate limited
  • Configuration changes need review, publishing and rollback

Capabilities you turn on as needed

  • Cluster configuration and shared certificates: sites, certificates and ECH keys live in Litemesh / Consul KV; write once and the whole cluster hot-reloads
  • Multi-tenant routing (IDS): after route matching and before forwarding, your Go plugin identifies the tenant and decides
  • On-demand certificates: customers bind their own domains and certificates are issued at handshake time
  • Release control: changes go to a draft, are published after you confirm the diff, and roll back in one step
  • Compiled plugins: litegate build --with compiles middleware, load balancers, service discovery and other plugins into the binary

Use case 12 · MCP

Configure and troubleshoot with AI

  • You would rather describe what you need in plain language than memorize configuration fields
  • Production requests return 404 / 502 and you want the AI to check route matching, upstream reachability and error logs
  • You use Claude Code, Cursor, Claude Desktop or another MCP-capable assistant

Two ways to connect

stdiowrite config locally
$ claude mcp add litegate -- \
    litegate mcp -config /etc/litegate/config.yaml

The AI starts a separate LiteGate process that reads and writes configuration files, and the running gateway hot-reloads them. Use absolute paths for sites_dir and similar directories in config.yaml, because relative paths resolve against the AI client's working directory.

config.yamlSSE: connect to the running gateway
mcp:
  enabled: true
  port: 9900
  token: "generate with litegate -secret"
terminal
$ claude mcp add --transport sse litegate \
    http://127.0.0.1:9900/sse \
    --header "Authorization: Bearer <token>"

Both expose the same tools. Runtime diagnostics such as recent requests, error logs, runtime status and tunnels need the SSE connection to the running gateway; a stdio process cannot see gateway traffic.

What the AI can do

  • Create sites: reverse proxies, static sites, service bindings, TCP/UDP streams, Forward sites; enable OIDC / JWT / API keys
  • Validate before applying: validate_site_config checks strictly, preview_config_change shows the diff, and after saving verify_site sends a real request; rollback is one call
  • Troubleshoot: lookup_route simulates a request to show which route matches, test_upstream checks backend reachability, plus recent requests, error logs and certificate expiry
  • Service tags: generate tag templates and preview the routes they produce with the runtime parser

MCP tools can change and delete configuration: keep the SSE port on localhost or the private network and always set token. In production, turn on release control so the AI's changes land in a draft and are published only after you confirm.
