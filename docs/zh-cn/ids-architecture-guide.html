LiteGate Architecture Guide

IDS：把 SaaS 业务决策放到请求进入下游之前

一个业务中立、可插拔的请求决策接缝：验证流量、补充可信上下文、选择隔离实例池，或者在不访问下游时直接响应客户端。

1. 为什么需要 IDS

普通网关擅长按 Host、Path 和 Header 匹配静态路由，但 SaaS 的流量方向经常只有在查询业务系统之后才能确定。

1内核不应该认识租户字段

不同企业使用 Tenant ID、App ID、组织、项目或自定义凭证。把这些字段写进内核，会让网关与某一种 SaaS 模型永久耦合。

2认证结果会影响选路

验证 JWT 只是开始。请求可能还要进入该租户的数据库、专属集群或指定版本；身份判断与物理流量方向需要在同一个业务决策中完成。

3策略来自外部状态

租户系统、Redis session、授权平台和配置中心中的状态会变化。仅靠静态路由规则无法表达“租户 A 去集群 A，租户 B 去集群 B”。

4拒绝请求不应访问下游

缺少凭证、权限不足或 session 失效时，Provider 应直接返回 401/403，而不是先把不可信请求发送到业务服务。

IDS 的目的不是再造一种 JWT 中间件。它提供的是“业务系统参与网关转发决策”的稳定接口，同时让 LiteGate 内核保持业务中立。

公共接口

type IDSProvider interface {
    Evaluate(
        ctx context.Context,
        input IDSInput,
    ) (*IDSDecision, error)
}

input.Request 是受限的只读请求视图，只公开 Method、Scheme、Host、Path、Query、Header、RemoteAddress 与带上限的 Body 读取；插件不能取得或修改 *http.Request。input.Options 是当前路由的不可变动态参数副本。

结果语义典型用途
Forward，无 Route验证通过，使用原路由默认下游开放平台验签、权限验证
Forward，有 Route验证通过，并约束服务发现候选实例租户隔离、版本灰度
Forward，有 RateLimit按插件返回的不透明主体 Key 动态限流租户套餐、App 配额
Respond由网关直接响应，不访问下游401、403、业务拒绝
errorProvider 或 Redis/租户系统等基础设施失败503，或显式 fail-open

IDSDecision 返回对象详解

IDSDecision 是 Provider 交给 LiteGate 的单次请求决策。它不是身份对象，也不固定 Tenant ID、App ID 或 SID；它只描述网关接下来应该执行什么。

type IDSDecision struct {
    Action    IDSAction
    Route     *RouteDecision
    RateLimit *RateLimitDecision
    Headers   http.Header
    Response  *DirectResponse
}

type RouteDecision struct {
    Selector map[string]string
    Meta     map[string]string
}

type RateLimitDecision struct {
    Key               string
    RequestsPerSecond float64
}

type DirectResponse struct {
    Status  int
    Headers http.Header
    Body    []byte
}
字段何时使用语义和约束
Action始终必填ActionForward 或 ActionRespond。零值和未知值会被视为插件错误并返回 500。
Route仅 Forward，可选为空表示使用路由配置的默认下游。Selector 是硬过滤边界；Meta 是该边界内的可回退偏好。空 map 等同于未指定该部分。
RateLimit仅 Forward，可选按不透明 Key 执行动态 QPS token bucket。Key 必须为 1–256 字节，QPS 必须大于 0；超限直接返回 429。
Headers仅 Forward，可选写入继续转发的请求。只有路由 allowed_headers 白名单允许的敏感 Header 才能投影；Authorization、Cookie、X-Forwarded-* 等保留 Header 不能覆盖。
Response仅 Respond，必填直接返回客户端，不访问服务发现和下游。Status 必须在 100–599；Headers 是响应头，Body 是响应体字节。

合法组合

验证通过，默认下游

&plugin.IDSDecision{
    Action: plugin.ActionForward,
}

不选择实例池、不注入 Header，也不动态限流。

验证通过，完整 SaaS 决策

&plugin.IDSDecision{
    Action: plugin.ActionForward,
    Route: route,
    RateLimit: quota,
    Headers: trustedHeaders,
}

限流通过后，按 Selector/Meta 过滤并访问下游。

业务拒绝

&plugin.IDSDecision{
    Action: plugin.ActionRespond,
    Response: &plugin.DirectResponse{
        Status: 401,
        Body: []byte("unauthorized"),
    },
}

这是正常业务结果，不能用 error 代替。

插件或依赖故障

return nil, err

例如 Redis 超时或租户系统不可用，由 fail_policy 决定拒绝还是放行。

禁止的组合

错误返回原因
Respond 没有 Response网关不知道应该返回什么。
Respond 同时带 Route、RateLimit 或请求 HeadersRespond 已终止转发，这些字段语义冲突。
Forward 同时带 Response不能同时继续转发和直接响应。
RateLimit Key 为空或 QPS ≤ 0无法构造有效、隔离的 token bucket。
返回 nil decision 且 nil error属于不明确的插件结果，网关按 500 处理。

业务拒绝和系统错误必须分开：凭证无效、权限不足、配额业务规则拒绝使用 Respond；Redis、数据库、HTTP 依赖失败才返回 error。只有 error 会受到 fail_policy 影响。

3. IDS 与现有网关能力的边界

IDS 负责

  • 读取请求并执行自定义验证
  • 查询 Redis、租户系统或授权平台
  • 生成可信的下游 Header
  • 选择 Selector 和可选 Meta
  • 直接拒绝或响应客户端

IDS 不负责

  • 内置 Tenant ID、App ID 或 JWT 模型
  • 返回任意下游 URL 绕过路由边界
  • 替代现有 rewrite 和 redirect
  • 替代完整的 Body 转换引擎
  • 让内核管理业务 session 生命周期
能力应该使用
/oldapi 固定改为 /apirewrite
通知浏览器访问新地址redirect
JWT 对应哪个租户、数据库或集群IDS Provider
静态 Basic/JWT 认证auth
标准 OAuth2/OIDC 回调与登录会话remote_auth

4. IDS 主要解决的场景

场景 A：开放平台 App ID + Secret

  1. 插件从请求读取 App ID、时间戳和签名。
  2. 从本地缓存、Redis 或租户系统取得 Secret。
  3. 完成签名、防重放和权限验证。
  4. 生成可信业务 Header，返回 Forward；通常无需返回 Route，继续走默认服务。

仓库提供了兼容旧 Body MD5 协议的完整实现，参见 OpenAPI MD5 IDS Provider。

场景 B：应用共享，数据库独立

  1. 登录 Provider 在业务登录链路中建立 JWT/session 与租户资源的绑定。
  2. API Provider 从请求读取 token，在 Redis 查询 session。
  3. 将不透明的数据库引用投影给共享应用。
  4. 下游应用只使用可信网关上下文连接对应租户数据库。

场景 C：每个租户进入独立集群

  1. Provider 根据 token 找到租户。
  2. 租户 A 返回 Selector {cluster: a}，租户 B 返回 {cluster: b}。
  3. 服务发现只在对应硬边界内选择健康实例，不发生跨租户降级。

场景 D：租户级灰度或升级

Provider 返回租户硬 Selector，并附加 Meta {version: v2}。v2 已部署则进入灰度池；若该集群忘记部署 v2，只回到同一 Selector 的默认实例。

场景 E：老系统迁移

确定性的 /oldapi → /api 使用 rewrite；IDS 查询租户迁移状态，并选择旧集群或新集群。这样路径变换和业务选路各自保持清晰，无需扩大 IDS 接口。

5. Selector 是边界，Meta 是偏好

Selectorcluster = A
→
Meta 命中version = v2
→
A 集群 v2 实例
Selectorcluster = A
→
Meta 未命中无 v2 实例
→
A 集群默认实例

不会发生：A 集群没有 v2 时进入 B 集群，也不会误入 A 集群中另一个可选版本。Selector 永不跨越，Meta 只在边界内回退。

6. 动态配置、密钥与缓存

新架构没有全局 ids_providers。路由 options 每次 Evaluate 都传入当前值，因此站点配置或服务标签热更新后无需重启网关。

options:
  token_header: Authorization
  policy_ref: order-read
  redis_ref: tenant-session-prod

options 应存放策略值或安全引用，不放 Redis 密码、数据库口令。Provider 用引用从自己的 Secret Manager 或配置中心解析秘密，并作为并发单例复用 HTTP、Redis、DB 客户端。

进程内短缓存
→
Redis
→
租户系统
→
回填缓存
  • 缓存键包含所有影响验证和选路的维度。
  • 不存在的数据使用较短负缓存。
  • 登录、刷新、注销主动失效关联键。
  • 设置 TTL、外部访问超时和连接池上限。

租户或 App 动态限流

RateLimit: &plugin.RateLimitDecision{
    Key:               session.SubjectRef,
    RequestsPerSecond: session.QPS,
}

执行顺序为 IDS → 动态限流 → 服务发现 → Proxy。超限直接返回 429，不会查询实例或访问下游。网关不解释 Key 的业务含义，并在写入本地缓存或 Redis 前将其哈希。

7. 完整样例

路由配置

action:
  type: proxy
  service_name: shared-saas-service
  ids:
    provider: saas-session
    fail_policy: deny
    options:
      token_header: Authorization
      policy_ref: order-read
    header_projection:
      allowed_headers:
        - X-Tenant-Ref
        - X-Database-Ref

Provider 决策

func (p *Provider) Evaluate(
    ctx context.Context,
    input plugin.IDSInput,
) (*plugin.IDSDecision, error) {
    token := first(input.Request.Header(input.Options.Get("token_header")))
    session, err := p.lookupSession(ctx, token)
    if err != nil { return nil, err }
    if session == nil {
        return &plugin.IDSDecision{
            Action: plugin.ActionRespond,
            Response: &plugin.DirectResponse{Status: http.StatusUnauthorized},
        }, nil
    }
    return &plugin.IDSDecision{
        Action: plugin.ActionForward,
        Headers: http.Header{
            "X-Tenant-Ref":   {session.TenantRef},
            "X-Database-Ref": {session.DatabaseRef},
        },
        Route: &plugin.RouteDecision{
            Selector: map[string]string{"cluster": session.Cluster},
            Meta: map[string]string{"version": session.PreferredVersion},
        },
        RateLimit: &plugin.RateLimitDecision{
            Key: session.SubjectRef,
            RequestsPerSecond: session.QPS,
        },
    }, nil
}

如果只验证数据并进入默认下游，省略 Route。业务拒绝返回 Respond；只有 Redis 不可用、租户系统超时等系统故障才返回 error。

8. 安全与实现原则

  1. 默认 fail-closed：fail_policy: deny，只有明确接受绕过风险时才使用 allow。
  2. Header 最小授权：客户端携带的内部 Header 先清理，插件生成的值还要经过投影白名单。
  3. 并发安全：Provider 是跨请求单例，不在普通字段保存单次请求状态。
  4. 限制请求体：读取 Body 时限制大小并恢复 Body，保证下游仍可读取。
  5. 结构化选路：只返回 Selector/Meta，不允许任意目标 URL。
  6. 配置加载校验：Provider 为空或未注册时拒绝加载站点配置。

一句话总结：IDS 让用户在网关和下游之间插入自己的 SaaS 决策逻辑，而 LiteGate 只负责安全地执行 Forward、Respond、Header 投影和候选池选择。
