场景 1

发布网站或前端应用

  • 你有一个静态网站、博客，或者 Vue / React 打包出来的 dist 目录
  • 想要 HTTPS，但不想自己申请和续期证书
  • 前端刷新任意路由都要能打开，/api 要转给后端

最小配置

sites/www.yaml静态网站
site: https://www.example.com
file_server: ./public
sites/app.yaml单页应用 + 接口
site: https://app.example.com
/api:
  proxy: localhost:8080
  strip_prefix: true   # 后端不需要 /api 前缀时
spa: ./dist              # 未知路由回退 index.html

写 https:// 前缀就会开启 HTTPS：HTTP 请求跳转到 HTTPS，证书自动申请。只写域名时默认是纯 HTTP。

再进一步

  • compress: true 开启 gzip / brotli / zstd 压缩（站点有子路由时写在 / 路由里）
  • response_headers 统一加安全响应头
  • 旧域名、旧路径用 redirect 跳转并保留原路径
  • 文档目录直接用 markdown 渲染成网页，文件下载区用 list 目录浏览
  • 前端包放进 KV，多台网关自动同步、保留历史版本
sites/www.yaml
site: https://www.example.com
response_headers:
  X-Frame-Options: DENY
/docs:                      # Markdown 渲染成网页
  markdown: {root: ./docs}
/:                          # 有子路由时，根处理写进 / 路由
  file_server: ./public
  compress: true

场景 2

给多个后端做 API 网关

  • 一个域名下有多个服务，要按路径分给不同后端
  • 同一个服务有多个实例，需要负载均衡、健康检查和重试
  • 要统一处理跨域、限流、请求头，不想每个服务各写一遍

最小配置

sites/api.yaml按路径分流
site: https://api.example.com
/users: localhost:8080
/orders: localhost:8081
/orders/export: localhost:8082  # 更具体的路径优先
sites/api.yaml多实例
site: https://api.example.com
proxy:
  to: [10.0.0.5:8080, 10.0.0.6:8080]
  lb: least_conn     # 默认 round_robin
  health: /health     # 探测失败自动摘除
  retry: 2

路由的先后顺序不影响结果，按路径精确度和优先级排序；两条匹配条件完全相同的路由会直接报错。WebSocket、gRPC 不需要额外配置。

再进一步：治理规则写在路由下面

  • cors：预检请求由网关直接应答
  • rate_limit：按路由或按客户端 IP 限流
  • request_headers / response_headers：增删请求头，前缀 - 表示删除
  • cache：反向代理缓存；熔断、加权分流、会话保持见命名 Service
  • 多个路由共用的配置抽成 snippets，用 import 引用
sites/api.yaml
site: https://api.example.com
/api:
  proxy: localhost:8080
  cors:
    allowed_origins: [https://web.example.com]
  rate_limit: {rate: 10, key: ip}
  request_headers:
    -X-User-Id: ""   # 丢弃客户端伪造的身份头

场景 3 · Magic Ingress

服务一上线，路由自动出现

  • 后端跑在 Docker、Swarm、Kubernetes，或者注册在 Consul / Litemesh
  • 服务经常上线、扩容、下线，不想每次都改网关配置
  • 前端和多个后端服务要挂在同一个域名下，避免跨域

最小配置：网关只写前端，后端自己声明

sites/app.yaml网关上只写这一次
site: https://app.example.com
spa: ./dist

https://app.example.com/ 是前端，/api/orders、/api/users 随服务注册自动出现，实例下线自动摘除。

docker-compose.yml
services:
  orders:
    image: acme/orders
    labels:
      litegate.http.host: app.example.com
      litegate.http.path_prefix: /api/orders
  users:
    image: acme/users
    labels:
      litegate.http.host: app.example.com
      litegate.http.path_prefix: /api/users
服务元数据
litegate.http.host=app.example.com
litegate.http.path_prefix=/api/orders
litegate.http.strip_path=true   # 可选：转发时去掉前缀
服务元数据命名资源写法
litegate.http.routers.orders.match.hosts=app.example.com
litegate.http.routers.orders.match.path_prefix=/api/orders
litegate.http.routers.orders.middlewares=orders-limit
litegate.http.middlewares.orders-limit.ratelimit.qps=100
litegate.http.services.orders.retry.attempts=2
litegate.http.services.orders.healthcheck.path=/healthz

Kubernetes 用户可以直接使用标准 Ingress 和 Gateway API 资源，LiteGate 内置控制器，不需要额外安装组件。

场景 4 · Connect

没有公网 IP，也能把内网服务发出去

  • 服务在家里、办公室或客户机房，没有公网 IP 或不能开放入站端口
  • 私有化部署的系统需要被云端访问，原来靠 frp 或开放 MQ 端口
  • 希望 TLS 在内网终止，云端只转发密文、看不到明文

工作方式

内网节点（Home）主动拨向云端（Cloud），一个 Cloud 可以接入多个 Home，每个 Home 只能发布被授权的域名。Home 上照常写站点文件，开启 publish_sites 后这些站点就通过隧道对外提供服务。

Home · config.yaml
connect:
  client:
    enabled: true
    name: home
    remote: https://connect.example.com
    token_file: /etc/litegate/secrets/home.token
    publish_sites: true

场景 5 · Forward

在本机安全连上云上的数据库

  • MySQL、Redis、SSH 在云上 VPC 里，开发者需要从本机连接
  • 不想给数据库开公网端口，也不想维护跳板机或 VPN
  • 内网服务器需要统一经过一个出口访问公网 API（正向代理）

最小配置

网关 · streams + sites服务端
# streams/rds.yaml：不单独监听，只供 Forward 使用
name: rds
protocol: tcp
listen: false
proxy: 10.0.0.20:3306
---
# sites/db-tunnel.yaml：域名锁定到这个 Stream
site: https://db-tunnel.example.com
forward:
  target: {type: stream, name: rds}
  token_file: ./secrets/forward.token
开发机客户端
$ litegate forward \
    --remote https://db-tunnel.example.com \
    --local 127.0.0.1:3306 \
    --token-file ./rds.token
$ mysql -h 127.0.0.1 -P 3306 -u app -p

流量走 443 加密，客户端无法改变目标；Stream 上的 IP 限制、会话上限和超时照常生效。

场景 6

证书不用再手动管

  • 想要 HTTPS，但不想再跑 Certbot 和定时任务
  • 家庭网络 80 端口被封，或者需要 *.example.com 泛域名证书
  • 本地开发也想用受信任的 HTTPS；或 SaaS 客户要绑定自己的域名

最小配置

站点写 site: https://域名（或 https: true）就会自动申请证书，到期前自动续期，默认走 HTTP-01。80 端口不通时，在 config.yaml 配好 DNS 服务商，匹配的域名自动改走 DNS-01，失败会退避重试。

  • 内置阿里云、Cloudflare、华为云、腾讯云，其他服务商用插件扩展
  • 只封 80 端口时，也可以设 default_challenge: tls-alpn 走 443
  • 集群模式下证书存在 KV，一个节点签发、所有节点共享
config.yaml · 家庭网络
auto_cert:
  enabled: true
  email: admin@example.com
  dns_providers:
    - name: cloudflare
      type: cloudflare
      enabled: true
      domains: ["*.home.example.com"]
      config:
        api_token: env://CF_API_TOKEN

再进一步：连访问哪个网站都加密（ECH）

普通 HTTPS 在握手时会明文暴露域名。开启 ECH 后，网络上只能看到一个公共名称，真实域名被加密在 ClientHello 里。网站继续使用普通 ACME 证书，没启用 ECH 的客户端照常访问。

config.yaml
ech:
  enabled: true
  public_name: ech.home.example.com  # 外界唯一可见
  dns_provider: cloudflare
  domains: [app.home.example.com]   # 要隐藏的站点

场景 7

给后台加登录和防护

  • 内部工具、管理后台要挡住匿名访问，或者接入公司的 SSO
  • API 要校验 JWT，后端只想拿到已验证的用户信息
  • 要防扫描、防刷接口、只允许内网访问某些路径

最小配置

sites/app.yaml按路径分别保护
site: https://app.example.com
/admin:
  proxy: localhost:8081
  ip_restriction:
    allow_ips: [10.0.0.0/8, 192.168.0.0/16]
/api/login:
  proxy: localhost:8080
  rate_limit: {rate: 1, key: ip}
proxy: localhost:8080
sites/api.yamlJWT 校验
site: https://api.example.com
/api:
  proxy: localhost:8080
  auth:
    type: jwt
    jwks_url: https://auth.example.com/.well-known/jwks.json
    issuer: https://auth.example.com

再进一步

  • OIDC / OAuth2 单点登录：在 config.yaml 定义 auth_providers，路由里用 remote_auth 引用，登录后把 claims 注入请求头给后端（需要 Redis 保存会话）
  • 已有认证服务：用 Forward Auth 把鉴权交给它
  • 规则型 WAF、扫描防护、CSRF 防护；多路由共用的策略定义成命名中间件，用 use 引用

场景 8 · Notify Hub

给浏览器推送实时消息

  • 配置变更、任务完成、工单提醒需要实时通知前端或其他服务
  • 不想部署 MQTT，也不想自己写 WebSocket 服务、维护连接表
  • 多台网关、多个后端实例都要收到同一条消息

最小配置：两条路由

sites/app.yaml
site: https://app.example.com
/notify:                 # 发布：Header key 选择主题
  publish: notify.{header.key}
/events/config:          # 订阅配置通知
  subscribe: notify.config
任何语言
$ curl -X POST http://10.0.0.10/notify \
    -H "key: config" \
    -H "Content-Type: application/json" \
    -d '{"type":"config.changed","version":42}'
app.js浏览器原生 API
const events = new EventSource('/events/config')
events.onopen = () => reloadAll()        // 连上先刷新
events.onmessage = e => reload(JSON.parse(e.data))
main.go只依赖标准库
sub := &notify.Subscriber{
    URL:     "https://app.example.com/events/config",
    OnOpen:  cache.ReloadAll,
    OnEvent: cache.Apply,
}
go sub.Run(ctx)   // 自动重连、随机退避

网关通过 NATS 把消息送到每个节点，推送、心跳和断线重连都在网关处理，业务后端仍是无状态 HTTP 服务。示例是在线通知；发布和订阅的鉴权请用 JWT、Forward Auth 等配置。需要逐条送达时启用 JetStream 离线消息。

场景 9 · L4

TCP / UDP 转发，网站和 TLS 服务共用 443

  • 需要转发数据库、DNS、游戏服务这类非 HTTP 流量
  • 服务器只开了 443，Redis TLS、gRPC 等服务也想走这个端口

最小配置

streams/独立端口
# streams/mysql.yaml
site: tcp://:3307
proxy: 192.168.1.100:3306
---
# streams/dns.yaml
site: udp://:5353
proxy: 192.168.1.100:53
streams/redis.yaml共用 443
site: tcp://redis.example.com   # 按 SNI 匹配
proxy: 10.0.0.30:6380

网关在 TLS 握手前读取 SNI，匹配的连接整条转给上游，其余照常进入 HTTPS。MySQL、PostgreSQL 这类先明文握手的协议，请用场景 5 的 Forward。

场景 10

状态页、控制台与生产部署

  • 想给用户一个公开的服务状态页，或者给运维一个实时控制台
  • 要把 LiteGate 跑成系统服务或容器，并接入现有监控
  • 出问题时想快速知道请求走了哪条路由、为什么被拒绝

一段配置开启

sites/status.yaml公开状态页
site: https://status.example.com
status:
  title: 服务状态
  host: "*"              # 默认只显示当前站点
  show_instances: true   # 显示每个后端实例

也可以挂在已有站点下：/status: {status: {}}。数据来自网关的真实流量，不需要另装探针。

config.yamlDashboard 控制台
dashboard:
  enabled: true
  port: 9999
  username: ops
  password: "$2a$10$..."   # litegate -hash 生成

实时吞吐与延迟、路由与服务标签、访问日志、证书、Connect 隧道和已编入插件都在这里，也能在线编辑站点。建议只在内网开放该端口。

常用命令

  • litegate -init 生成目录和示例配置，litegate -t 上线前校验
  • litegate systemd 生成 systemd 单元，litegate healthcheck 给容器做健康检查
  • Prometheus 指标、访问日志、Trace ID 贯穿请求链路；官方 Grafana 面板导入即用
  • 路由为什么没命中，可以让 AI 通过 MCP 模拟请求查给你看，见场景 12
terminal
$ litegate -init         # 生成目录与示例配置
$ litegate -t            # 校验配置
$ litegate -hash 'pwd'   # bcrypt 密码哈希
$ litegate systemd       # 输出 systemd 单元

场景 11

从一台 VPS 长成多租户 SaaS

  • 多台网关组成集群，站点和证书需要统一管理
  • 要按租户识别、放行、选择租户专属实例和限流
  • 配置变更需要审核、发布和回滚

按需打开的能力

  • 集群配置与证书共享：站点、证书、ECH 密钥统一放在 Litemesh / Consul KV，写一次全集群热加载
  • 多租户选路（IDS）：路由匹配后、转发前，由你的 Go 插件识别租户并决策
  • 按需证书：客户绑定自己的域名，握手时按需签发
  • 配置发布控制面：修改先进草稿，确认差异后发布，可一键回滚
  • 编译期插件：litegate build --with 把中间件、负载均衡、服务发现等插件编进二进制

场景 12 · MCP

用 AI 配置和排障

  • 不想记配置字段，希望用自然语言描述需求，让 AI 生成并落地
  • 线上请求返回 404 / 502，想让 AI 查路由命中、上游连通和错误日志
  • 用 Claude Code、Cursor、Claude Desktop 等支持 MCP 的 AI 助手

两种接入方式

stdio本机写配置
$ claude mcp add litegate -- \
    litegate mcp -config /etc/litegate/config.yaml

AI 拉起一个独立的 LiteGate 进程来读写配置文件，正在运行的网关自动热加载。config.yaml 里的 sites_dir 等目录建议写绝对路径，因为相对路径按 AI 客户端的工作目录解析。

config.yamlSSE：连正在运行的网关
mcp:
  enabled: true
  port: 9900
  token: "用 litegate -secret 生成"
terminal
$ claude mcp add --transport sse litegate \
    http://127.0.0.1:9900/sse \
    --header "Authorization: Bearer <token>"

两种方式的工具相同。查看最近请求、错误日志、运行状态、隧道等运行时诊断需要用 SSE 方式连接正在运行的网关；stdio 进程看不到网关的流量。

AI 能做什么

  • 建站：反向代理、静态站、服务绑定、TCP/UDP Stream、Forward 站点；开启 OIDC / JWT / API Key
  • 先校验后生效：validate_site_config 严格校验，preview_config_change 展示差异，保存后 verify_site 实际请求验证，可一键回滚
  • 排障：lookup_route 模拟一次请求看命中哪条路由，test_upstream 测后端连通，查最近请求和错误日志、证书到期
  • 服务标签：生成标签模板，并用运行时解析器预览会生成的路由

MCP 工具能修改和删除配置：SSE 端口只在本机或内网监听并始终设置 token；生产环境建议开启配置发布控制面，让 AI 的改动先进草稿，确认后再发布。
